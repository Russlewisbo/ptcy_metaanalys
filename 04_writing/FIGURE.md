# Figure preparation guide

How the numbered manuscript figures (and their appendix companions) are
built, and how to regenerate them. Source of truth for all figure logic is
[`Manuscript_LancetHaem_draft.qmd`](Manuscript_LancetHaem_draft.qmd) — this
document explains *why* the code looks the way it does, including two bugs
that were found and fixed during development.

## Regenerating everything

```bash
cd 04_writing
quarto render Manuscript_LancetHaem_draft.qmd --to html
```

Rendering the manuscript is sufficient. Each figure-producing chunk calls a
`save_fig()` helper (defined in the `setup` chunk) that writes the plot to
`figures/` in three formats — **PNG** (quick viewing), **PDF** (print/LaTeX),
and **SVG** (editing/web) — every time the document is rendered. There is no
separate figure-export script; the manuscript render *is* the export
pipeline. Do not hand-edit files in `figures/` — they will be overwritten on
the next render.

## Design: why individual studies are frequentist but the pooled estimate is Bayesian

Figures 2–4 show **two different kinds of estimate on the same plot**, and
this is intentional, not an inconsistency:

- **Per-study points** (dot + 95% CI) are raw per-study odds ratios computed
  directly from each study's 2×2 event table (`metafor::escalc`, Wald CI).
  They are *not* model output.
- **The "Bayesian pooled" row** (diamond + posterior density) is the actual
  primary Bayesian model's (M1) posterior median and 95% credible interval.

This split exists because **the M1 model has no per-study treatment
effect**. The model formula is:

```r
events_n | trials(denom_n) ~ ptcy_binary + tp_early + (1 | study_id)
```

`ptcy_binary` is a single fixed effect shared across all studies; the
`(1 | study_id)` random intercept only captures study-level variation in
*baseline* event rates, not in the treatment effect itself. So there is
exactly one Bayesian posterior per outcome/comparison (the pooled effect),
and no separate posterior exists for any individual study. Overlaying a
posterior on every row would require refitting with a random *slope*
(`(1 + ptcy_binary | study_id)`), which was not done for the primary
analysis. Anyone asking "why isn't there a violin on every row?" — this is
why.

## The half-density overlay on the pooled row

The pooled row shows both a point/CI (diamond) and a one-sided density
("half-eye") of the full posterior draws, rising **above** the row's
baseline only (not mirrored below it, i.e. not a symmetric violin). This is
built manually (no `ggdist` dependency) inside `forest_study_bayes()`:

```r
dens <- density(log(bayes$draws), n = 512)   # density on log scale, matches scale_x_log10()
dens_df <- data.frame(x = exp(dens$x), ymin = bp_y,
                       ymax = bp_y + dens$y / max(dens$y) * 0.85)
# ... later ...
geom_ribbon(data = dens_df, aes(x = x, ymin = ymin, ymax = ymax), inherit.aes = FALSE, ...)
```

`bp_y` is the pooled row's discrete y-position; the ribbon's `ymin` is
pinned there and `ymax` rises by up to 0.85 of a row's height, scaled to the
density's own maximum.

## Bug #1 (fixed): mislabelled posterior cache files

Several cached posterior files in `03_models/post_block9/` are named as if
they were the primary model (M1) but actually contain **M2** (steroid-
mediation-adjusted) draws — identifiable by the presence of a
`b_steroid_pct_c` coefficient:

- `post_c1_os.rds`, `post_c2_os.rds`, `post_c1_cmv.rds`, `post_c2_cmv.rds`

**Do not use these for the primary/M1 estimate.** The manuscript instead
loads the true M1 `brmsfit` objects directly and extracts draws with
`as_draws_df()`:

```r
m1_c1_os  <- readRDS(file.path(model_dir, "m1_c1_os.rds"))
m1_c2_os  <- readRDS(file.path(model_dir, "m1_c2_os.rds"))
m1_c1_cmv <- readRDS(file.path(model_dir, "m1_c1_cmv.rds"))
m1_c2_cmv <- readRDS(file.path(model_dir, "m1_c2_cmv.rds"))
m1_c1_bsi <- readRDS(file.path(model_dir, "m1_c1_bsi.rds"))
m1_c1_ifi <- readRDS(file.path(model_dir, "m1_c1_ifi_any.rds"))
m1_c1_bk  <- readRDS(file.path(model_dir, "m1_c1_bk.rds"))
```

`post_m1_post2020.rds` and `post_m1_haplo.rds` (used in the CMV sensitivity
figure) were checked and are correctly labelled M1 draws — only the four
files listed above are mislabelled. This was confirmed by comparing pooled
ORs against the manuscript's reported text values (e.g. C1 OS M1 should be
0.79 [0.73–0.85]; the mislabelled `post_c1_os.rds` instead yields 0.86
[0.77–0.96], which is the M2 value). `AGENTS.md` (the project memory file)
still shows the old, buggy loading pattern in its "How to Load Data"
example and has not yet been corrected — treat that example with caution
until it is.

## Bug #2 (fixed): ggplot2 discrete-axis reordering with per-layer subsets

`forest_study_bayes()` and `forest_study()` each draw the pooled estimate
and the individual studies as **two separate `geom_pointrange()` layers**,
built by `subset()`-ing the same `slab` factor column (one layer excludes
the pooled row, the other contains only it). This triggers a real ggplot2
gotcha:

> With `drop = TRUE` (the default for discrete scales), ggplot2 trains the
> y-axis **per layer**. A factor level that is *exclusively* present in one
> layer (e.g. "Bayesian pooled", which only appears in the pooled-only
> layer) gets appended to the axis in order of **first appearance across
> layers**, not according to its actual index in the factor's `levels()`.

Concretely: the "individual studies" layer trains the axis first (its 40
levels, in ascending-OR order), and only then does the "pooled" layer
introduce "Bayesian pooled" as a "new" value — which gets pushed to the
*end* of the axis (visually the top), even though it was defined as level 1
(which should render at the bottom, per ggplot2's normal convention of
level 1 → bottom, highest level → top).

This was invisible before the density overlay was added (a diamond floating
at the top of a forest plot looks like a normal, if slightly unconventional,
summary-row placement). It became a visible bug once the density ribbon was
introduced, because the ribbon is anchored using `bp_y` — the *intended*
level-1 position — while the pooled row's point/label had been silently
bumped to the opposite end of the axis by the layer-training quirk. Result:
the density appeared floating next to an unrelated study row instead of
next to "Bayesian pooled".

**Fix:** force the axis to respect the factor's defined level order,
overriding ggplot2's per-layer training:

```r
scale_y_discrete(limits = slab_levels)   # forest_study_bayes()
scale_y_discrete(limits = levels(pd$slab))  # forest_study()
```

If you add any *new* multi-layer forest-style plot in this document (i.e.
one that splits pooled vs. per-study rows into separate `geom_*()` calls
sharing one factor column), add the same `scale_y_discrete(limits = ...)`
line, or the same misalignment will reappear silently.

## Adding a new outcome to the Bayesian forest-plot pipeline

1. Load the analytic CSV (`data_c1_<outcome>.csv` or `data_c2_<outcome>.csv`)
   in the `setup` chunk via `load_data()`.
2. Load the true M1 `brmsfit` object (`m1_c1_<outcome>.rds` /
   `m1_c2_<outcome>.rds`) — **verify it lacks `b_steroid_pct_c`** before
   trusting it as M1 (see Bug #1).
3. Compute its summary with `bayes_pooled(model)`.
4. Call `forest_study_bayes(dat, studies_df, title, subtitle, bayes_summary)`
   to build the panel; combine multiple panels with `patchwork` (`/` or
   `plot_layout()`), roughly proportioning panel heights to `k`.
5. Assign the combined plot to a variable and call
   `save_fig(plot, "FigureN_description", width = ..., height = ...)`
   before returning it from the chunk, so PNG/PDF/SVG are written
   automatically on every render.
